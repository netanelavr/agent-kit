# Kit rules

Vendor-neutral always-on rules. Cursor loads them via the `kit-*.mdc` wrappers in this folder. Claude Code (2.1.277+, no `CLAUDE.md`) and Codex load the repo-root `AGENTS.md`, which points here.

---

# Comment why

Comments preserve **intent and danger**, not narration.

## Keep / add

- WHY (tradeoff, incident, constraint)
- Landmines (“do not reorder”, “must match protocol X”)
- Workarounds tied to a quirk/ticket
- Non-obvious invariants

## Remove / avoid

- WHAT the next line does
- Restating the function name
- Motivational / tutorial prose
- Comments that rot on trivial edits

## Calibration

Bad:
```ts
// Increment the retry counter
retryCount += 1
```

Good:
```ts
// Do not switch to exponential backoff here; upstream rate-limits on burst, not average.
retryCount += 1
```

Prefer deleting a weak comment over replacing it with another weak one. Never tidy away a landmine comment for style.

# Delegate

Default is **inline or a skill**. Escalate to a **subagent** only when isolation or parallelism pays for itself. Do not spawn agents for tiny lookups.

| Situation | Do this |
|---|---|
| One-shot (changelog, format, short lookup) | Skill or inline |
| Long research / noisy logs that would flood the chat | One subagent |
| Same method over independent units and wait time hurts | Parallel fan-out — one worker per unit |
| Unit B needs A, or both edit the same file | Sequential; parent applies shared writes |

Parallelize only when units do not need each other’s mid-run output, writes do not overlap, and each unit has named paths. Without worktrees, do not parallel-edit the same working tree.

Fleet: default 2–3, soft max ~4 unless the user asks for more. Skip orchestration for single-file work.

Every subagent starts blank. Pass: goal, scope (and what not to touch), decisions already made, constraints, done criteria, and proof artifacts when claims matter.

Parent keeps aggregation, git/PR/shared config, and the user-facing summary. If one unit fails, mark it and keep aggregating — never treat a missing unit as a pass.

# Keep diff

Only lines that must change for the outcome should appear in the diff.

## Do not

- Reorder object keys, imports, class members, or enum values “for neatness”
- Alphabetize or sort lists that were not sorted before
- Move unrelated lines when inserting a new entry — insert without displacing neighbors

## Do

- Touch only what the change requires
- Add new imports/entries next to related ones without reshuffling the rest
- Reorder only when the user explicitly asks

If a formatter would reshuffle a whole file, prefer the smallest scoped edit that still compiles.

# Humanize

Write like a clear engineer, not a brochure.

## Ban

- Em dashes as separators (use hyphen with spaces, period, or restructure)
- Stock AI words: delve, tapestry, leverage, utilize, facilitate, streamline, paramount, pivotal, meticulous, holistic, robust, comprehensive, multifaceted, harness, foster, bolster, seamless, cutting-edge, game-changing, revolutionary, groundbreaking, nuanced, intricate, elevate, empower, unleash
- Openers/closers: “In today’s…”, “It’s worth noting…”, “At its core…”, “In summary…”, “Happy coding!”
- Narrating code comments that only restate the next line
- AI co-author trailers / “Generated by …” attribution
- Over-format: bold-label bullets, uniform list lengths, tricolon every line

## Prefer

- Plain words (“use”, “improve”, “important”)
- Mixed sentence length
- Short lowercase commit subjects; no marketing in bodies
- Sparse READMEs: what it does, not why it’s amazing

# Work loop

Gates for multi-step work. Invoke the named skills; do not copy their bodies here.

## Plan first

If the task needs **3+ steps** or crosses a boundary: `kit-plan`, then wait for explicit approval before coding. One-line local fixes may proceed.

## Keep the main chat clean

Long research, noisy logs, and parallel analysis: **one subagent per task**, per `kit-delegate`. Tiny lookups stay inline. Pass goal, scope, constraints, and done criteria. Do not dump raw research into the parent thread.

## Simpler path

Before a complex change: one question - is there a smaller path? If yes, `kit-minimize`. Do not debate every line.

## Sign-off

Before claiming done: `kit-prove` with live artifacts. Prefer an **isolated checker** (new subagent that sees only claims + done criteria, not the build chat). The builder's self-report is not proof.

## Capture the lesson

If you repeated a mistake class, or the user had to steer you: offer `kit-capture-lesson`. Do not silently rewrite always-on rules.

## Autonomy

Try to close **local, reversible** failures without asking. Stop and ask when the next step is destructive, touches production, or needs a product choice.
